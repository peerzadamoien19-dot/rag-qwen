# RAG Chatbot with Qwen and Streamlit

A Retrieval Augmented Generation (RAG) application that lets you upload a PDF and ask questions about its contents. Answers are generated by the Qwen language model using only the text found in your document.

Built with Python, Streamlit, FAISS and Hugging Face Inference Providers.

---

## What is RAG?

A language model only knows what it learned during training. It cannot answer questions about your lecture notes, your company handbook, or a paper published last week.

RAG solves this by giving the model the relevant text at question time.

The process has two phases.

**Phase 1: Indexing (runs once per document)**

1. Read the PDF and extract its text.
2. Split that text into small overlapping chunks.
3. Convert each chunk into a numerical vector using an embedding model.
4. Store those vectors in a FAISS index.

**Phase 2: Answering (runs for every question)**

1. Convert the question into a vector using the same embedding model.
2. Search the FAISS index for the closest matching chunks.
3. Send those chunks and the question to Qwen.
4. Return the generated answer.

---

## Why embeddings matter

An embedding turns text into a list of numbers. Text with similar meaning produces similar numbers.

This allows the system to search by meaning rather than by keyword.

For example, a user asking "how do I remove a directory?" will still match a passage that says "deleting folders with rmdir", even though the two share no words. A keyword search would find nothing.

## Architecture

| Layer | Technology | Role |
|---|---|---|
| Frontend | Streamlit | Browser based chat interface |
| Document processing | pypdf | Text extraction from PDFs |
| Embeddings | sentence-transformers (all-MiniLM-L6-v2) | Converts text to vectors |
| Vector store | FAISS | Stores and searches vectors |
| Generation | Qwen via Hugging Face | Writes the final answer |

### Two models, two jobs

This project uses two models, and they are not interchangeable.

The **embedding model** is small (around 80 MB) and runs locally. It only produces vectors for searching. It cannot write text.

**Qwen** is the language model that writes answers. It runs on Hugging Face partner infrastructure rather than locally, because a model of that size requires far more memory than a typical laptop or free hosting tier provides.

## Project structure

```
rag-qwen/
├── app.py              Streamlit interface and chat logic
├── ingest.py           PDF reading and text chunking
├── indexer.py          Embedding generation and FAISS index
├── retriever.py        Similarity search
├── generator.py        Prompt construction and Qwen API calls
├── requirements.txt    Python dependencies
└── .gitignore          Files excluded from version control
```

Each file handles one stage of the pipeline. This keeps the code readable and allows several people to work in parallel without conflicts.

## Setup

### Requirements

- Python 3.11 or later
- A free Hugging Face account

### 1. Clone the repository

```bash
git clone https://github.com/peerzadamoien19-dot/rag-qwen.git
cd rag-qwen
```

### 2. Create a virtual environment

```bash
python -m venv venv
```

Activate it:

```bash
# Windows
venv\Scripts\activate

# macOS and Linux
source venv/bin/activate
```

### 3. Install dependencies

```bash
pip install -r requirements.txt
```

This installs torch as a dependency of sentence-transformers, so the first install may take several minutes.

### 4. Add your Hugging Face token

Create a token at https://huggingface.co/settings/tokens with permission to call Inference Providers.

Create a file at `.streamlit/secrets.toml`:

```toml
HF_TOKEN = "hf_your_token_here"
```

This file is listed in `.gitignore` and must never be committed.

### 5. Run the application

```bash
streamlit run app.py
```

The app opens in your browser at `localhost:8501`.

## How to use

1. Upload a PDF using the sidebar.
2. Wait for indexing to complete. The sidebar shows the chunk count when ready.
3. Type a question in the chat box.
4. Read the answer, and expand "Sources used" to see which chunks the model received.

The first upload is slow because every chunk must be embedded. Subsequent questions are fast, since the index is cached for the session.

## Testing individual components

Each module can be run on its own for debugging. Place a PDF named `test.pdf` in the project root first.

```bash
python ingest.py      # Verify text extraction and chunking
python indexer.py     # Verify embedding and index creation
python retriever.py   # Verify that relevant chunks are retrieved
python generator.py   # Verify the full pipeline end to end
```

## Configuration

Key settings and where to change them:

| Setting | File | Default | Effect |
|---|---|---|---|
| `chunk_size` | ingest.py | 500 | Characters per chunk |
| `overlap` | ingest.py | 100 | Characters repeated between chunks |
| `top_k` | retriever.py | 3 | Number of chunks retrieved per question |
| `MODEL` | generator.py | Qwen/Qwen3.8-27B | Which Qwen model answers |
| `PROVIDER` | generator.py | novita | Which provider serves the model |
| `max_tokens` | generator.py | 500 | Maximum answer length |

### A note on providers

Hugging Face routes inference requests to partner providers such as Novita, Together AI and Fireworks. Each partner serves a different set of models, and those sets change over time.

Naming the provider explicitly avoids automatic routing failures. To see which models are currently available to your account:

```bash
hf models ls --warm --no-truncate --expand inferenceProviderMapping
```

## Limitations

- Only text based PDFs are supported. Scanned documents produce no extractable text.
- Large documents take several minutes to index on CPU.
- The index is held in memory and is lost when the session ends.
- Answer quality depends on retrieval quality. If the relevant passage is not among the retrieved chunks, the model cannot use it.

---

## Possible extensions

- Persist the FAISS index to disk so documents are indexed only once.
- Support multiple documents in a single index.
- Add source page numbers to each retrieved chunk.
- Replace fixed size chunking with semantic or paragraph aware splitting.
- Add a reranking step to improve retrieval precision.
